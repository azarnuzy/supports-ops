Dari kata “Claim” ke transaksi yang aman

Setelah lesson ini, Anda dapat membaca satu fitur SupportOps sebagai rangkaian keputusan domain—bukan sekadar React, HTTP, dan Prisma.

Snapshot kode: commit 5c559c1 · 14 September 2026

1. Mulai dari perilaku, bukan framework

Seorang Human Agent melihat Ticket yang sudah Escalated di Shared Human Queue, menekan Claim, lalu Ticket berpindah ke My Tickets. Hanya satu Human Agent boleh berhasil.

Bahasa domain menjawab “apa arti perilaku ini bagi bisnis?” Bahasa teknis—React mutation, HTTP POST, transaksi Prisma—menjawab “bagaimana perilaku itu diwujudkan?”

CONTEXT.md menetapkan arti dan istilah yang dihindari. Karena itu kode memakai claimTicket, ESCALATED, dan HUMAN_HANDLING, bukan sinonim seperti “assign case” atau status “pending”. Inilah Ubiquitous Language: kosakata yang dibentuk bersama dan dipakai konsisten dalam diskusi, dokumentasi, dan kode. Microsoft Learn menjelaskan tujuan yang sama: mengurangi salah paham dan membuat model mencerminkan maksud bisnis.

2. Sembilan konsep, dari first principles

Domain adalah ruang masalah yang hendak diselesaikan; di sini, operasi dukungan pelanggan. Subdomain membagi kemampuan yang berhubungan—misalnya Ticket handling, Channel delivery, Knowledge, dan Workspace administration. Pembagian ini adalah lensa analisis, bukan daftar Bounded Context resmi SupportOps. DDD biasanya membedakan core, supporting, dan generic subdomain agar investasi desain mengikuti nilai bisnis. Sumber resmi.

Bounded Context adalah batas tempat satu model dan satu arti istilah berlaku. Context Map mencatat hubungan antar-konteks serta cara mereka berintegrasi. SupportOps saat ini memiliki satu konteks bahasa untuk seluruh monorepo (docs/agents/domain.md); maka apps/api, apps/platform, dan packages/channels bukan otomatis Bounded Context terpisah. Tidak ada Context Map formal—masuk akal untuk bentuk saat ini, tetapi perlu ditinjau jika model independen mulai mempunyai arti istilah yang berbeda.

Entity memiliki identitas yang bertahan saat atribut berubah. Model Ticket mempunyai id; status dan assignee-nya dapat berubah tanpa menjadikannya Ticket baru (apps/api/prisma/schema/ticket.prisma:1–39). Value object tidak memiliki identitas, ditentukan oleh nilainya, dan idealnya immutable. Claim memakai enum TicketStatus sebagai nilai terkontrol (apps/api/prisma/schema/enums.prisma:51–56), tetapi repo tidak membentuk rich value object untuk status tersebut. Definisi resmi entity dan value object.

Aggregate adalah batas konsistensi transaksi dengan satu entity sebagai root; invariant adalah aturan domain yang harus selalu benar di dalam batas itu. Dalam flow Claim, Ticket dapat dibaca sebagai aggregate root karena transisi Ticket dan catatan CLAIMED dibuat atomik. Ini interpretasi terhadap kode, bukan deklarasi eksplisit repo. Invariant-nya: hanya Ticket berstatus ESCALATED tanpa assignee yang boleh berpindah ke tepat satu Human Agent. Aggregate sebaiknya kecil dan hanya memasukkan data yang memang harus konsisten bersama. Sumber resmi.

Anti-Corruption Layer (ACL) menerjemahkan semantik sistem luar ke model sendiri. parseWhatsAppWebhook mengubah payload Meta menjadi WhatsAppInboundEvent, sedangkan mapWhatsAppDeliveryStatus mengubah sent menjadi SENT (packages/channels/src/index.ts:66–112,132–227). Dengan begitu bentuk Meta tidak menyebar ke Ticket handling. Ini contoh adapter bergaya ACL, walau repo tidak memberinya label formal tersebut. Pola ACL resmi.

Buka glossary ringkas untuk mengulang sembilan istilah ini.

3. Trace end-to-end: Claim

  1. UI chat.tsx:243–246,599–607 hanya menampilkan tombol bila scope unassigned, status ESCALATED, dan pengguna adalah Human Agent. Klik memanggil mutation.
  2. Server state tickets.hooks.ts:158–160 menjalankan request dan menginvalidasi query setelah selesai agar daftar kembali cocok dengan server.
  3. Client contract packages/api-client/src/index.ts:315–324 mengirim POST /tickets/:id/claim dan menerjemahkan HTTP 409 menjadi TicketAlreadyClaimedApiError.
  4. Boundary apps/api/src/app.ts:48–69 memuat auth dan Workspace context sebelum memasang ticketsRouter. Route di tickets/router.ts:123–135 mengecek role, memanggil use case, lalu mengembalikan 409 bila sudah diklaim.
  5. Invariant tickets/services.ts:339–358 menjalankan satu conditional UPDATE dan menulis AI Activity CLAIMED dalam transaksi yang sama.
  6. Side effects Setelah commit, tickets/services.ts:359–361 menerbitkan perubahan queue dan mengatur ulang timer. Route memulai Handoff secara terpisah (tickets/router.ts:129–131), sehingga kegagalan summary tidak membatalkan Claim.
  7. Output UI menerima Ticket baru, meng-refresh cache, dan kalah-race ditampilkan sebagai pesan “just claimed by another Human Agent” (chat.tsx:527–532).
await tx.ticket.updateMany({
  data: { assignedHumanAgentId: humanAgentId, status: "HUMAN_HANDLING" },
  where: { assignedHumanAgentId: null, id: ticketId, status: "ESCALATED" },
});

Predikat where adalah aturan bisnis sekaligus concurrency guard. Dua request boleh datang bersamaan, tetapi setelah satu update menang, request kedua tidak lagi menemukan baris yang memenuhi syarat. Kebenaran berada di database, bukan di kondisi tombol UI atau event realtime. ADR-0005 menegaskan prinsip itu pada docs/adr/0005-sse-for-realtime-single-widget-channel.md:15.

4. Apa yang diterapkan, dipilih, dan belum diterapkan?

Diterapkan saat ini

  • Ubiquitous Language nyata dari glossary sampai nama enum, fungsi, UI, dan error.
  • Invariant Claim ditegakkan atomik bersama AI Activity, bukan dipercayakan kepada UI.
  • Model eksternal Meta diterjemahkan di package Channel sebelum masuk ke alur internal.

Trade-off / keputusan sadar

  • Satu konteks bahasa dan modular monolith menghindari koordinasi antar-service. ADR-0001 (docs/adr/0001-monorepo-app-and-package-topology.md:3–7) hanya mengekstrak package ketika ada batas nyata seperti reasoning versus transport.
  • Model domain bersifat relatif anemic: aturan Claim hidup di service function, bukan method pada entity. Ini lebih sederhana bersama Prisma, tetapi penemuan aturan bergantung pada penelusuran service.
  • Handoff berjalan setelah Claim. Konsistensi kuat dipakai untuk ownership; summary dan pengiriman memakai recovery terpisah agar kegagalannya tidak merebut kembali Ticket.

Best practice eksternal yang belum diterapkan

  • Tidak ada Context Map formal atau klasifikasi subdomain resmi.
  • Tidak ada rich domain entity/value object yang mengenkapsulasi transisi status; panduan tactical DDD merekomendasikan perilaku berada dekat entity.
  • Tidak ada abstraksi Aggregate eksplisit. Menambahkannya sekarang belum otomatis memperbaiki fitur; layak dilakukan bila aturan lifecycle tersebar dan mulai tidak konsisten.
Failure modes: menamai folder sebagai Bounded Context tanpa perbedaan model; mengandalkan canClaim di browser sebagai invariant; atau memasukkan seluruh Handoff/network delivery ke transaksi Claim sehingga lock hidup selama I/O.

Alternatif yang relevan: rich domain model dapat memusatkan transisi; database constraint atau serializable transaction dapat memperkuat aturan yang lebih kompleks; microservices dapat memisahkan konteks yang benar-benar independen. Belum ada kebutuhan nyata dalam flow ini yang membayar kompleksitas tersebut.

5. Cek pemahaman

Jawab dari ingatan sebelum membuka jawabannya.

Mengapa tombol Claim yang disembunyikan bukan invariant?

Browser dapat stale atau dipanggil langsung. Conditional update di transaksi adalah titik yang menentukan hanya satu Claim berhasil.

Apakah apps/api dan apps/platform dua Bounded Context?

Tidak. Repo menyatakan satu konteks bahasa; pemisahan deployable atau folder saja tidak membuktikan model yang berbeda.

Mengapa status Meta perlu diterjemahkan?

Agar vocabulary dan perubahan provider berhenti di boundary Channel, bukan bocor ke model serta use case Ticket.
