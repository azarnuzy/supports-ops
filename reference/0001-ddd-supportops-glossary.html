DDD dalam bahasa SupportOps

Gunakan lembar ini untuk membedakan konsep DDD dari bentuk kode yang kebetulan dipakai hari ini.

Domain
Ruang masalah bisnis: pada SupportOps, menangani dukungan pelanggan dari pesan masuk sampai Resolution.
Subdomain
Bagian kemampuan bisnis. Secara analitis: Ticket handling, Channel delivery, Knowledge, serta Workspace administration. Klasifikasi ini belum menjadi keputusan formal repo.
Ubiquitous Language
Kosakata bersama domain expert dan developer, dipakai konsisten dalam percakapan, dokumentasi, dan kode. Sumber SupportOps adalah CONTEXT.md.
Bounded Context
Batas tempat satu model dan bahasanya berlaku. SupportOps saat ini sengaja memakai satu konteks bahasa; folder atau deployable bukan otomatis Bounded Context.
Context Map
Peta hubungan dan pola integrasi antar-Bounded Context. Repo belum memiliki Context Map formal karena hanya mendokumentasikan satu konteks.
Entity
Objek yang kesinambungannya ditentukan identitas, bukan kesamaan atribut. Ticket dengan id tetap Ticket yang sama ketika status berubah.
Value Object
Nilai tanpa identitas, dibandingkan dari isinya dan idealnya immutable. Enum TicketStatus adalah nilai terkontrol, tetapi bukan rich value object tersendiri.
Aggregate
Batas konsistensi transaksi dengan satu root. Ticket dapat dibaca sebagai calon aggregate root untuk Claim, tetapi repo tidak menamainya secara eksplisit.
Invariant
Aturan yang harus selalu benar. Claim: hanya Ticket ESCALATED yang belum memiliki assignee dapat berpindah ke satu Human Agent.
Anti-Corruption Layer
Adapter yang menerjemahkan model eksternal agar tidak mencemari model internal. Parser di packages/channels menerjemahkan payload dan status Meta ke bentuk SupportOps.

Tiga pertanyaan saat membaca kode

  1. Istilah bisnis apa yang sedang diwujudkan?
  2. Aturan apa yang tidak boleh dilanggar?
  3. Di batas mana bentuk data diterjemahkan?
